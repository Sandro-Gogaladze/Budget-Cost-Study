Find the context budget that costs the least per correct answer

Three axes, one cheap model, and a result nobody has published: the economically optimal context budget. Raw dollars fall as you tighten the budget. Success falls too. Somewhere between them, dollars-per-correct-answer has a minimum — and that minimum is the number an engineer actually needs.

What dropping the memory axis buys you

a smaller study that answers a sharper question

Cutting probes removes the most labour-intensive third of the design — probe categories, checkers, admission gates, position balancing, the probe-tax control, the three-condition ablation. What remains is not a weakened study. It is a different one, and on a cheap model it is arguably the better one.

Three axes with one knob is enough for a complete claim: as you tighten the context budget, success falls, run-to-run consistency falls faster, and raw cost falls — so the dollars you pay per correct answer traces a U. Find the bottom of that U and you have the number every deployed agent is currently guessing.
Keep one column and you keep the option

Log note_text in full anyway — the actual summary the model produced at every compaction. It costs nothing, and it means the entire memory axis can be added later, offline, without re-running anything. If a reviewer asks "what does summarization destroy?", that is a week of analysis over traces you already own instead of $4,000 of new runs. Dropping the memory axis today should not mean losing the ability to answer it.

01

Which Gemini

this is the most consequential choice in the plan

The cheapest model is not the right model. The reliability axis needs a baseline pass rate away from both floor and ceiling — a strategy cannot lower a success rate that is already zero, and consistency is only measurable where outcomes actually vary. Published DeepSWE numbers make the choice for us:

Gemini 3.5 Flash37%~$1–2 (est.)Primary. 37% is close to the statistically ideal operating point — maximum outcome variance, room to fall and rise, no ceiling compression. It is also the older generation, which makes it half of a free generational pair.
Gemini 3.7 Flash65.0% ±2$2.18Second model, if budget allows. Newer generation → the trend result. Higher baseline means more ceiling compression on easy tasks.

Recommendation

Primary = Gemini 3.5 Flash. At 37% pass@1 it sits near the maximum of p(1−p), which is exactly where a consistency effect is easiest to detect. Add Gemini 3.7 Flash as the second model only in tier C. Treat Flash-Lite as a cost fallback, not a starting point — saving $300 is a bad trade for a study with no measurable signal.

Two properties of Gemini that shape the whole design

1M context window

FULL is a true uncompacted control on every DeepSWE task — the longest run is ~276K, well inside the window. No overflow policy needed, no runs lost to the ceiling.

It also reframes the question: at 1M tokens the only reason to compact is money and latency. Which makes cost the primary axis.

Implicit caching, on by default

90%discount on cached input, automatic for 2.5-and-newer models, minimum ~2K tokens. Nothing to enable.

No cache_control plumbing, unlike Anthropic — the cost axis becomes observable for free.

We set the budgets

Because the window is 1M and we choose LOOSE/MEDIUM/TIGHT ourselves, task selection can prioritise solvability over length. A 40K-context task still compacts hard at a 16K budget.

This inverts the selection order from the frontier-model plan — and it is what makes a cheap model viable.

Verify in E0 — a known failure mode

There are reports of implicit caching not engaging on Gemini 3 Flash when tools are defined in the request. We are probably safe: mini-swe-agent does not use native tool-calling — it asks the model to emit a bash block in plain text and parses it, so no tool schema is sent. But the entire cost axis rests on that, so E0 checks the returned cached-token count before anything else runs. If caching is not firing, find out on day one for $10, not in week six.

02

The cost model — do this before you spend anything

an afternoon of arithmetic that predicts the whole cost axis

Agent input cost is not linear in run length — it is roughly quadratic, because every step re-sends the entire history. That single fact dominates everything, and with a 90% cache discount it produces a clean, testable prediction you can derive before making a single API call.

The per-call cost

Let  p     = input price per token
     0.1p  = cached input price          # Gemini implicit caching: 90% off
     L_t   = context length at step t
     d_t   = new tokens appended since the previous call

cost(call t)  =  0.1p · L_(t-1)   +   p · d_t   +   p_out · out_t
                 ^^^ the cached prefix    ^^^ the new suffix

FULL over n steps, context growing to L:
     input ≈ p·L  +  0.1p · Σ L_t  ≈  p·L·(1 + 0.05n)
     # each token is paid once at full price, then at 10% forever after

What a compaction costs and saves

A compaction rewrites the prefix -> the cache is void -> the next call pays
FULL price on the whole new view V.

     penalty  =  p · V            # = 10 x the cached rate on V
     saving   =  0.1p · (L - V)   per subsequent call

Break-even in calls:   m* = 10V / (L - V)

     V = 32K,  L = 120K   ->  m* ≈ 3.6 calls
     V = 64K,  L = 120K   ->  m* ≈ 11.4 calls
     V = 32K,  L = 200K   ->  m* ≈ 1.9 calls
The pre-registered cost prediction

Compactions are typically tens of calls apart, and m* is single-digit at a tight budget. So on Gemini, compaction does reduce raw dollars — monotonically as the budget tightens. The interesting quantity is therefore not raw cost. It is cost-of-pass: dollars ÷ probability correct. Raw cost falls; accuracy falls; the ratio has a minimum.

H-cost: cost-of-pass is U-shaped in the budget, with an interior minimum strictly below the NATIVE window. That minimum is the operating point. It is falsifiable — if cost-of-pass is monotone decreasing, the right advice is "compact as hard as you can," and if monotone increasing, it is "never compact." Either would be a real finding.

What this means for your bill

ArmRelative input costWhy
FULL1.00×longest histories, but every token is cached after its first appearance
LOOSE~0.7×few compactions, shorter tails
TIGHT~0.4×many compactions, but each view is small — plus summarizer calls, which you must add in
PRUNE~0.35×same shrinkage, no summarizer calls at all — the cheapest arm by construction, and therefore the one to beat

Budget consequence: your treatment runs are cheaper than your control runs. The grid costs less than runs × FULL-price, which is the opposite of the usual situation and worth a line in the paper.

Not included in any dollar figure here

Sandbox compute. Modal charges for container time and is not part of the API estimates. Local --env docker is free but serial: 800 runs at ~25 minutes each is two weeks of wall clock. Run 4–8 containers in parallel locally (2–4 days), or accept Modal's compute line item. Decide this in E0 — it is a schedule constraint, not a budget one.

03

The lean design

four strategies, three budgets, one control — nothing else

FactorLevelsServes
S strategyFULL · PRUNE · SUMMARIZE · RETRIEVE · SUMMARIZE_T0all three axes; T0 defends reliability
B budgetNATIVE · LOOSE · MEDIUM · TIGHTthe knob — set by E2 from measured data
T task~15 in-band tasks, from a ~40-task screenselection is the study's biggest risk — §05 E3
K seed0–4reliability. 0–9 on a subset in tier B+

Why each arm is in or out

  • FULL — the control, and on a 1M window it is a genuine one for every task.
  • SUMMARIZE — the suspect.
  • RETRIEVE — the comparator the headline is measured against. Must be strong: query on the current subgoal, hybrid BM25 + embedding, pin recent turns and every turn containing a file write, tuned on a disjoint dev slice and then frozen.
  • PRUNE — kept, and it earns its place on the cost axis specifically: it shrinks context with zero summarizer calls and zero embedding calls, so it is the cheapest possible strategy and the floor any clever method must beat.
  • SUMMARIZE_T0 — kept at TIGHT only. It is the answer to "your variance is just the extra stochastic call," which is the first thing anyone will say about the reliability claim. Cheap insurance.
  • EXTRACTIVE — cut it isolates rewriting from shrinking, which is a memory-mechanism question. Comes back with the probes.
  • FILES — cut changes the tool surface, so it is not a pure context intervention.
Pairing is not optional

With ~15 tasks, every comparison is within-task: same task, same seed, SUMMARIZE vs RETRIEVE at the same budget. Bootstrap resamples tasks, 10,000 draws. A between-task comparison at this N is a shrug with error bars.

The cheap-model bonus: partial credit

ctrf.json reports per-assertion results, so even a failing run yields a graded score. On a 37%-pass model most runs fail, and a binary outcome throws away almost all the information in them. Use ctrf_pass_fraction as a secondary continuous outcome — it is far more sensitive at low pass rates, and it is free. Keep reward as the pre-registered primary so the headline stays comparable to the leaderboard.

The figure the paper is built around

One plot. X-axis: context budget, tight → loose. Three normalised curves: success, consistency (all@5), and cost-of-pass inverted. Shade the band where cost-of-pass is within its bootstrap CI of the minimum. That shaded band is the recommended operating range — and it is the thing an engineer pins on the wall. Every experiment in §05 exists to draw it.

Standing rules

  • Everything paired, bootstrap over tasks, 10,000 draws.
  • Exclusions: error excluded and its rate reported; step_limit / cost_limit / timeout scored reward=0 and reported as per-arm rates.
  • One primary endpoint (§08). Everything else is secondary and labelled so; Holm within families.
  • Model (if it converges at this N): reward ~ strategy * budget + log_steps + (1|task). At 15 tasks, report the paired bootstrap as primary and the mixed model as support — not the other way round.
08

The pre-registration

filed after E3 selection and E4 freezing, before E5 — two hypotheses, both falsifiable

SETTING   DeepSWE, 15-task subset (selection: FULL-arm pass rate in [0.25,0.75]
          at K=4, then longest-first — fixed after E3), Gemini 3.5 Flash,
          K = 5 seeds, budget levels fixed by E2 before any treatment run.

DEFINE    pass1(A) = mean reward over runs of arm A
          all@5(A) = fraction of tasks where A succeeds on all 5 seeds
          Delta(A) = pass1(A) - all@5(A)
          cop(A,B) = mean cost per run / pass1    # dollars per correct answer

H1  RELIABILITY   Delta(SUMMARIZE) - Delta(RETRIEVE) > 0  at TIGHT
    one-sided, alpha = .025, task-level bootstrap, 10,000 resamples.
    Co-primary condition: CI for pass1(SUM) - pass1(RET) includes 0.
    # "same average, worse consistency" — both halves must hold

H2  COST          cop(SUMMARIZE, B) is U-shaped in B, with an interior
    minimum strictly below NATIVE. Tested by fitting cop across
    {NATIVE, LOOSE, (MED), TIGHT} and bootstrapping the argmin location.
    # falsified if cop is monotone in either direction — which would
    # itself be the practical answer: "always compact" or "never compact"

SECONDARY C_out; ctrf_pass_fraction as a graded success measure; raw cost
          per arm; cache-hit rate around compaction events; PRUNE as the
          zero-overhead cost floor; strategy x budget interaction.

FROZEN    retriever_cfg_hash, slot_prompt_hash, budget grid, task subset,
          exclusion rules, K, price table date.
          Later changes are reported as dated deviations.
Why the endpoint is a gap, not a variance ratio

For binary outcomes, mean within-task variance is E[p(1−p)] = m − m² − Vartasks(p), bounded above by 0.25 and reaching it only if every task is exactly a coin flip. A pre-registered "≥2× the variance at equal means" would commit you to something close to mathematically unsatisfiable even if you are entirely right. The pass¹ − all@k gap says the same thing with no ceiling — and it is the form a practitioner can act on: how often does a task that usually works fail this time?
