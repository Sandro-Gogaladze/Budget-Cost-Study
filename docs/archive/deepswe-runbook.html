01

Why DeepSWE can carry this alone

the case for going single-benchmark first

The handbook treats Gaia2 and DeepSWE as co-primary: Gaia2 the microscope, DeepSWE the flagship. Focusing on DeepSWE first is not a descope — it is the arm that produces the paper's external validity, and three facts say it can stand on its own.

Length is real

DeepSWE runs are genuinely long, so a normal production budget forces compaction by itself. Nothing to argue about: no artificial threshold, no stress-test caveat.

The grader is as good

1.4%verifier disagreement with an independent judge (n=735), vs 32.4% for SWE-Bench Pro. That is the same league as Gaia2's 98% human agreement.

The cache story lives here

Long runs build long stable prefixes — which is exactly where prompt caching pays, and exactly what a rewrite destroys. The cost inversion is far more dramatic on DeepSWE than on a 19K-token phone task.

The second fact is the important one. The handbook's stated reason for needing Gaia2 was its near-perfect verifier. DeepSWE's verifiers were independently audited and disagree with a judge on 1.4% [0.7–2.5] of rollouts. That argument no longer forces a second benchmark.

What we give up by starting here — honestly

  • Cheap iteration. A gaia2-mini run costs cents; a DeepSWE run costs dollars and takes tens of minutes in a container. Debugging is slower and every mistake is more expensive. Mitigation: §04 builds a 3-task smoke slice and a replay harness so most iteration never calls a model at all.
  • One domain. A coding-only result invites "does this generalize?" Mitigation: Gaia2 returns in weeks 8–11 as a generalization arm — same code, ~200 runs, one budget pair — not as a co-primary. That is a far cheaper way to buy the second domain than running both tracks from week 1.
  • Task count. 113 tasks total, and our study subset will be ~30. Confidence intervals will be wide unless the analysis is paired. §07 makes pairing non-optional.
Decision

DeepSWE-first, Gaia2 as a generalization arm. All four workstreams point at DeepSWE through week 7. Gaia2 is re-entered in week 8 only if the DeepSWE result is real, and only at the scale needed to say "the effect is not coding-specific."

The gap that defines week 1

The DeepSWE paper does not publish per-run token or step distributions. It reports median output tokens and duration as efficiency metrics, but no context-length statistics — and explicitly enforced no step or cost cap. The "70–325 steps, 46–276K tokens" figures in the handbook are secondhand and must be re-derived. We cannot choose a budget grid until we measure this ourselves. That measurement is §04, and it is the first thing anyone runs.

03

The intervention point

one method, same as Gaia2 — different file

Gaia2 was a clean substrate because its agent rebuilds context through a single method. mini-swe-agent is cleaner still. Its design is deliberately linear: every step just appends to self.messages, and that list is both the trajectory record and the model input. There is no hidden state, no session, no memory layer to fight.

What we are subclassing — src/minisweagent/agents/default.py
@dataclass

class DefaultAgent:
    def run(self, task: str = "", **kwargs) -> dict
    def step(self) -> list[dict]
    def query(self) -> dict                 # ← THE ONE METHOD. "Query the model and return model messages"
    def execute_actions(self, message: dict) -> list[dict]
    def add_messages(self, *messages: dict) -> list[dict]
    def get_template_vars(self, **kwargs) -> dict
The rule that makes this clean

Never mutate self.messages. Build a derived view. Because mini-swe-agent uses one list for both the log and the prompt, mutating it would destroy our ground truth. Instead query() computes a view, sends the view to the model, and appends the response to the full log. Result: we keep a complete, uncompacted trajectory for every run in every arm — which is what makes the offline probe check (§05) and the cache re-pricing (§07) possible at zero extra API cost. This is strictly better than what we could do on Gaia2.

The strategy override

gaia/agent.py — the heart of the experiment
class ContextManagedAgent(DefaultAgent):
    """Changes ONLY which messages reach the model. self.messages stays the full log."""

    def __init__(self, *a, strategy="FULL", token_budget=None, summarizer=None,
                 summ_temperature=0.0, keep_recent=4, **kw):
        super().__init__(*a, **kw)
        self.strategy, self.token_budget = strategy, token_budget
        self.summarizer, self.summ_temperature = summarizer, summ_temperature
        self.keep_recent = keep_recent
        self.note = None
        self.compactions = 0
        self.summarizer_cost = 0.0          # model.cost does NOT see this — §06

    def build_view(self) -> list[dict]:
        msgs = self.messages
        if self.strategy == "FULL" or self.token_budget is None:
            return msgs
        if exact_tokens(msgs, self.model) <= self.token_budget:
            return msgs                     # under budget: nothing to do

        head, body = msgs[:2], msgs[2:]     # system + instruction — ALWAYS kept
        room = self.token_budget - exact_tokens(head, self.model)

        if self.strategy == "PRUNE":
            return head + keep_last_that_fit(body, room)

        if self.strategy == "RETRIEVE":
            q = subgoal_query(msgs)          # CURRENT subgoal, not the static task — §03.4
            return head + hybrid_topk(body, query=q, budget=room, pin=writes_and_last(body))

        if self.strategy in ("SUMMARIZE", "SUMMARIZE_T0", "EXTRACTIVE"):
            recent = keep_last_n(body, self.keep_recent)
            older  = body[:len(body) - len(recent)]
            if self.strategy == "EXTRACTIVE":
                self.note = extractive_span(older, target=room - exact_tokens(recent, self.model))
            else:
                t = 0.0 if self.strategy == "SUMMARIZE_T0" else self.summ_temperature
                self.note, c = self.summarizer(
                    SLOT_PROMPT + serialize(older, prior=self.note), temperature=t)
                self.summarizer_cost += c
            self.compactions += 1
            view = head + [{"role": "user",
                            "content": f"[COMPACTED MEMORY]\n{self.note}"}] + recent
            if exact_tokens(view, self.model) > self.token_budget:
                # recent turns alone can exceed a tight budget — shrink, then record it
                view, dropped = shrink_recent(view, self.token_budget, self.model)
                self.log_event("recent_overflow", dropped=dropped)
            return view
        raise ValueError(self.strategy)

    def query(self) -> dict:
        view = self.build_view()
        self.log_view(view)                  # exact prompt → cache re-pricing + probe_soft
        response = self.model.query(view)    # the model sees the VIEW…
        self.add_messages({"role": "assistant", **response})   # …the log keeps EVERYTHING
        self.log_usage(response)             # incl. cache_read / cache_creation tokens
        return response

03.1 · Three fixes baked into the code above

  • exact_tokens, not an estimate. The budget is the independent variable of the whole study. Measurement error in the treatment itself is the one place a heuristic is unaffordable — use the provider tokenizer or the usage counts returned by the previous call.
  • The recent-turns overflow guard. head + note + recent can exceed the budget when recent bash observations are large — which is exactly the tight-budget regime we care about. Without the guard, "32K budget" silently means "whatever the last four turns happen to weigh."
  • Summarizer cost is tracked separately. model.cost only sees the agent's own calls. If the summarizer's tokens are invisible, cost_limit lets the summarize arm run longer for the same nominal budget — a confound that would flatter our own suspect.

03.3 · "Temperature 0" is not determinism

Hosted APIs are not deterministic at temperature=0 — batching, routing and kernel non-determinism all leak through. Calling this arm "deterministic" is a claim a reviewer can falsify in one afternoon. Instead: measure it. Take one real compaction payload, call the summarizer 20 times at t=0, and report the exact output-identity rate in the paper. If it is 85%, we write 85%. The arm still does its job — it removes most of the added stochasticity — and the honesty is free.

03.4 · The retrieve arm must not be a strawman

Correction to the handbook

The handbook's pseudo-code retrieves with query=head[1]["content"] — the original task statement, fixed for the whole run. That is a weak retriever, and it is the comparator our headline claim is measured against. We were careful to insist on a strong summarizer so nobody could call it a strawman; the same care has to run in the other direction, or a reviewer will simply say we rigged the baseline. Worse: if retrieve is weak, summarize may beat it on the mean, and the "same average, worse reliability" framing collapses.

Specification for a strong RETRIEVE.

  • Query = the task instruction plus the last two turns (the current subgoal), not the task alone.
  • Corpus = prior turns chunked at command boundaries — one bash call and its observation per chunk.
  • Scoring = hybrid BM25 + embedding similarity. Embeddings are cents per run; there is no excuse for lexical-only.
  • Pins = always include the most recent keep_recent turns and every turn containing a file write or diff, regardless of score. An agent that forgets its own edits is not a retrieval baseline, it is a bug.
  • Tuning = tuned once on a held-out 5-task dev slice, then frozen and pre-registered as "best-effort strong baseline." Frozen before the treatment runs, so it cannot be tuned toward the result we want.

03.5 · Getting our agent into Pier

Pier ships a fixed roster of adapters — nop, oracle, antigravity-sdk, claude-code, codex, cursor-cli, gemini-cli, opencode, mini-swe-agent — and does not document a third-party agent hook. Two paths, and week 1 picks one:

Path A — fork (recommended)

Fork mini-swe-agent, add ContextManagedAgent, expose strategy / token_budget through AgentConfig. Pier's per-agent YAML already passes kwargs through, so the sweep becomes a config matrix. If the adapter drops unknown kwargs, fork Pier's adapter too — it is a thin shim.

simple two forks to maintain

Path B — model-side proxy

mini-swe-agent talks to models through litellm. Point it at a local proxy that rewrites the message list on the way out. Zero changes to agent or runner — and the same shim would work for claude-code and codex too, which is real optionality for the "extensible" claim.

portable sees messages, not agent state

Call: build A for the pilot — it is direct, and having the agent object gives us clean access to compaction counts and probe state. Keep B specified but unbuilt; it becomes the answer if we later want the same sweep on a different scaffold.

Do this on day one or pay for it twice

Log prompt_hash and the cache usage fields from the very first run. The handbook calls the cache-adjusted cost analysis "free — it's re-pricing traces we already have." That is only true if the traces contain the exact prefix boundaries. If we discover in week 6 that we never logged them, "free" becomes "re-run everything."

What we compute

  • Peak context per task — p10 / p50 / p90 / p99. This sets the budget grid.
  • The floor — system template + instruction.md tokens. Every budget must clear it with room to spare; the tightest budget is not allowed to be mostly system prompt.
  • Step counts and the observation-size distribution — which commands blow up context (a cat of a large file, a full test log).
  • Cost and wall clock per task — the real forecast, replacing the handbook's secondhand $0.61–$21 band.
  • Baseline pass rate per task at FULL.

Choosing the budget grid

Pick 4 values from the measured distribution, not from intuition:

LevelRuleIntent
FULLthe model's native windowcontrol — and it is what production does when it does nothing
LOOSE≈ p75 of peak contextcompaction fires on a minority of tasks — the gentle end of the curve
MEDIUM≈ p40most tasks compact at least once
TIGHT≈ p15, floored at 2.5× the headmost tasks compact ≥3× — but never degenerates into "no history at all"

Acceptance test for the grid: at LOOSE, ≥30% of subset tasks compact at least once; at TIGHT, ≥80% compact at least three times, and the median view still carries ≥1.5× the head in actual history. If a grid cannot satisfy both, the subset is wrong, not the grid.

The trap that would sink the subset

Selecting the longest tasks selects the hardest tasks. Rank by context length alone and we end up with a subset where the baseline pass rate is near zero — and a strategy cannot lower a success rate that is already on the floor. Two-stage selection: first filter to tasks whose peak context exceeds the TIGHT budget (they must actually compact); then keep only those with a FULL-arm pass rate in [0.2, 0.9]. Target 30. If fewer than 20 survive, widen K instead of widening the subset — more seeds on fewer tasks beats more tasks with no signal.

The FULL control has a ceiling of its own

On the longest tasks, an uncompacted history can exceed the model's own window. Policy, fixed before the runs: FULL = the model's native window, and any run that overflows it is recorded as exit_reason=context_overflow and reported as a separate rate per model, not silently scored. That overflow rate is itself a finding — it is the number that says "you cannot actually run this task without compacting," which is the premise of the whole paper.

The replay harness

Most of our iteration must not call a model. Because self.messages is preserved in full for every run, we can replay any trajectory through build_view() offline and check: does this budget fire? how many compactions? does the recent-overflow guard trip? what does the view look like at step 40? Build this in week 1. It converts most debugging from dollars into milliseconds, and it is the answer to "DeepSWE is too expensive to iterate on."

05

Probes on a coding benchmark

the hard part — and the trick that makes it cheap

Gaia2 let us inject an event into a simulated phone world and watch whether the fact reached a calendar write. DeepSWE has no world to inject into: there is a repo, a bash tool, and a verifier. The probe mechanism has to be rebuilt. It also has to be rebuilt without hand-writing a verifier for each of 113 tasks, or the arm is unaffordable.

The trick

Make the probe task-agnostic by checking the diff, not the task. A planted requirement that constrains how the agent edits code — a required tag, a forbidden API, a named constant — is checkable by one small function over git diff, identically for every task in the benchmark. One checker, 113 tasks, no per-task verifier work. This is what makes the mechanism story affordable on DeepSWE.

Where the fact is planted decides which condition it tests

PlacementLands inCompactable?Condition
appended to instruction.mdheadno — head is always kept(a) raw notes — the ceiling. A failure here is a reasoning failure, not a memory failure.
injected as a maintainer message at step kbodyyes(c) the real pipeline — survives compaction and must be recalled many steps later
written into a repo file the agent must readbody, as an observationyes(c), naturalistic variant — the fact arrives as tool output, not as an instruction

Condition (b) summary-only needs no agent run at all. We already log every pre-compaction history and every summary note, so: take the logged older block that contained the fact, take the note the summarizer produced from it, and ask whether the fact survived into the note. One cheap check per compaction event, zero agent runs. The (a)→(b) drop is the construction loss; the (b)→(c) drop is the retrieval loss. The most expensive-sounding part of the design turns out to be nearly free.

Scoring — three signals, one untouched

  • reward — DeepSWE's own verifier, unmodified. We never edit tests/. The benchmark's number stays the benchmark's number.
  • probe_hard — did the final diff honor the planted requirement? (the primary probe signal)
  • probe_in_note — did the fact survive into the summary? (condition b — construction loss)
  • probe_soft — was the fact still literally present in the final model view? (secondary; disambiguates "lost" from "present but ignored")
Scoring correction from the handbook

The handbook's probe check was a substring match, which fails a summary that faithfully writes "4pm" for "16:00" — inflating construction loss and our own headline effect. It also contradicts our stated adoption of NoLiMa's no-word-overlap probe design: we cannot demand semantic probes and score them lexically. Fix: every probe ships with an explicit accepted-forms set, and anything outside it goes to a cheap semantic checker whose agreement with a human is measured once on ~100 cases and reported.

Position counterbalancing — actually implemented

The handbook promised counterbalancing and then planted at a fixed step. Here the injection step k is drawn per run from the run's own step budget at the 25th, 50th and 75th percentile, balanced across the subset so every task sees every position across seeds. Position then enters the model as a covariate rather than as an unmeasured confound.

Also worth a paragraph in the paper

The summary always sits in the same slot — head + note + recent. We cite Lost-in-the-Middle as a confound but never vary the thing it warns about. Cheap defensive ablation, one budget, one strategy, ~150 runs: place the note before vs after the recent turns. If placement moves the result, we need to know before a reviewer asks.

07

How we measure

the four axes, in DeepSWE's units

Q1 · Success

DeepSWE's reward, analysed paired within task. With ~30 tasks, a between-task comparison throws away most of the power we have; the same task under two strategies at the same budget with the same seed is the unit of comparison. Report the budget curve per model, and look for the knee — the operating range engineers pin on the wall.

Q2 · Reliability

The headline endpoint has to change

The handbook pre-registers "≥2× the variance at equal mean" on a binary outcome. For Bernoulli outcomes, mean within-task variance is E[p(1−p)] = m − m² − Vartasks(p), which at a mean of 0.6 is bounded in [0, 0.24] — and reaches 0.24 only when every task is exactly a p=0.6 coin flip. A 2× ratio at equal means therefore requires the summarize arm to sit at the mathematical ceiling while retrieve is near-deterministic per task. We would be pre-registering a prediction that is nearly impossible to satisfy even if we are completely right.

Fix — the pre-registered primary endpoint becomes the consistency gap:

MetricDefinitionRole
pass¹ordinary mean success ratethe baseline the gap is measured against
all@kchance a task succeeds on all k runs renamed from pass^kthe handbook already flagged this is not standard pass@k; renaming costs nothing and prevents a misread table
Δ = pass¹ − all@kthe inconsistencyprimary pre-registered endpoint. Prediction: Δ(summarize) − Δ(retrieve) > 0 at TIGHT, CI excluding 0, while the pass¹ difference includes 0
C_out0–1 consistency; 1 = always-pass or always-fail, →0 = coin flipssecondary, continuous, reported per budget
variance ratioVar(summarize)/Var(retrieve)still reported — but with the feasible bound at the observed mean printed beside it, so the number is readable in context

Power, computed now. The variance-test power calculation is a binomial simulation — it needs no API calls and no pilot data. Run it in week 1 against a range of plausible effect sizes, and let it set K before we commit, rather than discovering in week 4 that the pilot was underpowered to inform the design it was supposed to inform.

Q3 · Cost — and this is where DeepSWE earns its place

On Gaia2 the cache story would be inferred. Here it is measured: litellm surfaces cache_read_input_tokens and cache_creation_input_tokens on every response, and DeepSWE runs are long enough that a stable prefix is worth real money. We report:

  • cost-of-pass = dollars per attempt ÷ probability correct = expected dollars per correct answer. Infinite at zero accuracy — which is the honest way to price an arm that saves tokens by failing.
  • observed cache hit rate per arm, straight from the provider counters. Prediction: near-total collapse in the summarize arm at every compaction, and recovery over the following turns until the next one.
  • re-priced cost under no-cache / warm-cache / cold-cache, from the logged prefix hashes. Costs nothing. Includes the once-an-hour user who always lands cold.
  • the accuracy-vs-cost Pareto, with and without cache. The question we are actually answering: does the token-saving option save money once you count the failures it causes and the cache it breaks?

Q4 · Memory

The 6 × 3 loss grid from §05 — six fact categories against construction loss, retrieval loss, and survival — per strategy and per model. The output is a sentence with numbers in it: "aggressive summarization destroys constraints and error-state signals at construction; numeric IDs survive the summary but are lost at retrieval."

The statistical model

reward ~ strategy * budget + position + log_steps + tool_error_rate + (1 | task) + (1 | repo)
  • The strategy × budget interaction is the test: does summarize degrade faster than prune and retrieve as the budget tightens?
  • A repo term as well as task: 30 tasks may span nearly 30 repos, and language and codebase style are real clusters. Drop it if it fails to converge — and say so.
  • Bootstrap CIs; multiplicity correction across the four axes; the analysis plan frozen and filed after the pilot, before the confirmatory runs.

Descope order — protecting the contributions, not just the budget

Correction to the handbook

The handbook's descope order drops the 3rd and 4th models second — but those are the older generations that produce the old-vs-new trends result, one of the four claimed contributions. Dropping them silently deletes a headline while the text says "the core result survives all of these." Older models are also the cheap ones. The order below protects the trend and spends the savings elsewhere.

  1. Drop the note-placement ablation and the Gaia2 generalization arm. −350 runs
  2. Drop K=10 deepening; keep K=5 everywhere. −150 runs
  3. Drop the frontier second model — keep the older generation. The trend needs a gap between generations, not three points on it. −1,050 runs
  4. Cut the budget grid from three treatment levels to two (LOOSE, TIGHT). −~800 runs
  5. Cut the subset from 30 tasks to 20, keeping the widest baseline-pass-rate spread.

What survives all five: one modern and one older model, two budgets, FULL / SUMMARIZE / RETRIEVE, K=5, the full probe taxonomy, the cache re-pricing, and the consistency gap. That is the paper — the reliability claim, the cache inversion, the memory taxonomy, and the generational trend all still stand.
