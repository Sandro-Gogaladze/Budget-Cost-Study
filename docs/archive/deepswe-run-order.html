How to read a run card

every experiment has the same seven fields — no exceptions

The uniformity is the point. If an experiment cannot fill all seven fields, it is not ready to run. In particular, an experiment with no decision rule is not an experiment — it is a way of spending money and finding out afterwards what you think.

Fairness rule

Whatever tuning effort SUMMARIZE gets, RETRIEVE gets the same, on the same dev slice, in the same experiment (E4). Tuning one arm and not the other is how a measurement paper turns into a rigged comparison — and it is the criticism that would land hardest, because our headline is literally summarize versus retrieve. Both configs are frozen together and hashed before a single confirmatory run.

The two fields people forget

prompt_hash and prefix_match_len. Every cache claim in the paper is reconstructed from these. Without them, "re-pricing is free" becomes "re-run the study." note_text in full. Storing the actual summaries is what makes condition (b), the memory taxonomy and every post-hoc question about what the summarizer wrote answerable without new runs. Both are cheap. Neither is recoverable later.

03

Assignment rules

how a run gets its probe, its seed and its injection step — deterministically

Every comparison in this study is paired. A task under SUMMARIZE at TIGHT is compared to the same task, same seed, same probe, same injection step under RETRIEVE at TIGHT. With thirty tasks, pairing is not a refinement — it is the difference between a detectable effect and a shrug.
assign.py — deterministic, reproducible, identical across arms
CATS = ["constraint","id","result","error","temporal","xref"]
POS  = ["Q1","Q2","Q3"]

def assign(task_idx: int, seed: int, median_steps_full: int) -> dict:
    """Depends ONLY on (task, seed). NOT on strategy, budget or model —
       so every arm sees an identical probe on an identical step. That is what
       makes the comparison paired."""
    cat = CATS[(task_idx + seed) % 6]                # Latin-square over tasks x seeds
    pos = POS[(task_idx + 2 * seed) % 3]
    frac = {"Q1": .25, "Q2": .50, "Q3": .75}[pos]
    # k comes from the FULL-arm median step count measured in E1 —
    # NOT from this run's own length, which differs by arm.
    k = max(2, round(frac * median_steps_full))
    return {"probe_category": cat, "probe_position": pos, "probe_step_k": k}
  • One probe per run. Six requirements in one run is a different task, not six measurements. Balance across runs instead — 30 tasks × 5 seeds gives 150 cells per (strategy, budget), against 18 category×position combinations: roughly 8 replicates each.
  • k is fixed in advance, from E1. If it came from the run's own length, a tight budget — which changes step count — would move the probe, and probe survival would be confounded with the treatment.
  • If the run ends before step k, the probe never fires: set probe_injected=False, keep the run in the reward analysis, exclude it from the probe analysis, and report the rate per arm. A systematic difference in that rate is itself informative.
  • Seed controls sampling only. The same seed number means the same probe and the same k in every arm; it does not mean the model behaves identically, and we don't pretend it does.

E5Probe validation & ceiling gates the memory axis105 runs
Question
For each of the six probe categories: can the model follow it when it is visible, how often is it satisfied by accident, and does adding it damage the task?
Varies
C ∈ all 6 categories, plus a no-probe control. Placement fixed at HEAD — the probe sits in the instruction, never compacted. This is condition (a), the ceiling.
Fixed
Dev slice, S=FULL, B=NATIVE, M=M1, K=3.
Size
5 × (6+1) × 3 = 105 runs · ~$250
Computes
  • Head compliance — probe_hard rate when the fact is visible. This is the ceiling for that category.
  • Base rate — how often the no-probe runs satisfy the checker anyway.
  • Compliance lift = head compliance − base rate. The usable signal.
  • Probe tax — Δreward between probed and no-probe runs.
  • Checker precision — hand-label ~100 diffs; report agreement with the automatic checker.
Gate
Admit a category only if lift ≥ 0.4, base rate ≤ 0.5, and probe tax CI includes 0. A probe the model cannot follow when it is looking straight at it measures reasoning, not memory. A probe satisfied by accident half the time measures nothing. Expect to lose one or two categories here — losing them now costs $250; losing them in week 9 costs the taxonomy.
Phase C · the gate — week 3
E6Pilot — go / no-go the decision250 runs
Question
Does the strategy move anything — success, consistency, or fact survival — end-to-end through the real pipeline, with a confidence interval?
Varies

S ∈ {FULL, SUMMARIZE, RETRIEVE} × B ∈ {LOOSE, TIGHT} (FULL at NATIVE only) × seed ∈ 0–4.

Probes: the two strongest categories from E5, L=INJECTED, positions balanced by §03.

Fixed
10 tasks drawn from the study subset spanning the baseline-rate range; M=M1; frozen E4 configs.
Size
50 + 100 + 100 = 250 runs · ~$500–1,300 · 2–3 days
Computes
  • Paired Δreward, SUMMARIZE vs RETRIEVE at TIGHT, task-level bootstrap CI
  • pass¹, all@5, and the gap Δ = pass¹ − all@5 per arm
  • Construction loss = 1 − probe_in_note rate (computed offline from the logged notes)
  • Observed cache-hit rate per arm — the first real look at the cost inversion
  • Truncation and overflow rates per arm
  • Observed effect sizes and variances → the input to E7
Gate

GO if any one holds with a CI excluding zero:

  • SUMMARIZE is ≥10 points worse on reward at TIGHT, or
  • pass¹ is comparable but Δ(SUMMARIZE) > Δ(RETRIEVE) — the thesis, and the outcome we want, or
  • construction loss is reliably above zero.

NO-GO: nothing moves and the CIs are tight. That is a real result — "modern models are robust to compaction on real long coding tasks" — and it is cheap to establish. Write it up as a short paper and stop; do not spend $20k looking for an effect the pilot says is not there.

Correction to the runbook's forecast

The runbook quoted $8k–20k. This is $10k–26k, because that figure omitted the census (E1a/E1b), the dev-tuning (E4), the probe validation (E5) and the probe-tax control (E8b) — roughly 450 runs of instrument-building. Those are not optional: they are the experiments that stop the expensive ones from being uninterpretable. Better to carry the honest number.

Descope order — in the order you actually cut

  1. E13 Gaia2 arm and E11 note placement. −350 runs
  2. E10 variance deepening; keep K=5 everywhere. −150
  3. M2, the frontier model — keep M3, the older generation. The trend needs a gap between generations, not three points on it, and M3 is the cheap one. −1,050
  4. Budget grid from three treatment levels to two — drop MEDIUM, keep LOOSE and TIGHT. −~800
  5. Study subset from 30 tasks to 20, keeping the widest baseline-rate spread. −~33%

What survives all five: ≈2,000 runs, $4k–10k — E0–E8b plus M3, two budgets, three strategies, K=5, every admitted probe category, the full cache re-pricing. That is still the reliability claim, the cache inversion, the memory taxonomy and the generational trend.

Standing analysis rules

  • Everything paired. Bootstrap resamples tasks, 10,000 draws, not runs — the task is the unit of generalization.
  • Exclusions, pre-registered. infra_error excluded and its rate reported. step_limit, cost_limit, timeout, context_overflow scored reward=0 and reported as separate per-arm rates. probe_injected=False excluded from probe analysis only.
  • Multiplicity. One primary endpoint. Everything else is secondary and labelled as such; Holm correction within each family.
  • The model: reward ~ strategy * budget + position + log_steps + tool_errors + (1|task) + (1|repo). Drop the repo term if it fails to converge, and say so.

The pre-registration, in the words you file

written after E6, before E8 — this is the whole commitment

Primary hypothesis and test
SETTING   DeepSWE, 30-task study subset (selection rule: peak context > TIGHT budget
          AND FULL-arm baseline pass rate in [0.25, 0.75], fixed after E1b),
          primary model M1 at its published reasoning effort, K = 5 seeds,
          budget level TIGHT (value fixed by E2 before any treatment run).

DEFINE    pass1(A)  = mean reward over all runs of arm A
          all@5(A)  = fraction of tasks where A succeeds on all 5 seeds

Why the endpoint is the gap, not a variance ratio

For a binary outcome, mean within-task variance is E[p(1−p)] = m − m² − Vartasks(p). At a mean of 0.6 that quantity cannot exceed 0.24, and it reaches 0.24 only if every task is exactly a p=0.6 coin flip. A pre-registered "≥2× the variance at equal means" would therefore require the summarize arm to sit at the mathematical ceiling while retrieve is near-deterministic per task — we would be committing to a prediction that is close to unsatisfiable even if we are entirely right. The pass¹ − all@k gap expresses the same idea with no ceiling, and it is the metric a practitioner can act on: how often does a task that usually works fail this time?
