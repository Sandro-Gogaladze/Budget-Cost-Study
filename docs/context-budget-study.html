The plan — one document, supersedes all previous volumes

What does the context budget cost a long-running agent?

Every deployed coding agent sets a token budget and compacts when it passes it. That budget is guessed, never measured. We sweep it on real coding tasks and measure three things: does success fall, does the agent get less consistent, and where is the dollar-per-correct-answer minimum? This version is built for a hard $200 ceiling on an unfiltered random sample — enough to draw all three curves, and to extend cleanly when more budget arrives.

01

The question, and the two hypotheses

the thesis in one page

An agent working a long task fills its context window. Every production system handles this the same way: set a budget, and when the history passes it, compact — usually by summarizing. Claude Code compacts well below its limit. Codex reportedly caps around 300K of a 1M window. The industry already believes max context is not best. Nobody has measured where the good range is.

We do not build a better summarizer. We measure what the budget costs — the exact knob every deployed agent already sets — and we sweep it, so no single value can be called cherry-picked. The measurement is the paper.

This framing does real work. The hardest objection to a study like this is "isn't your threshold artificial?" Here the threshold is the object of study, it is what every real system already does, and we sweep it rather than fixing it. The attack becomes the contribution. It also picks the right kind of paper: measurement papers that characterise a failure get accepted; papers that bundle a fix get rejected.

H1 · Reliability

As the budget tightens, summarizing keeps a similar average success to retrieval but becomes far less consistent run-to-run — the same task passes on some seeds and fails on others.

Endpoint: Δ = pass¹ − all@k. Falsified if the contrast CI includes zero.

H2 · Cost

Raw dollars fall monotonically as the budget tightens. Accuracy falls too, so cost-of-pass is U-shaped with an interior minimum below the native window.

Falsified if monotone — which is itself the practical answer: always compact, or never compact.

H2 carries this version of the study. Cost per run is measured exactly, not sampled — the only noisy term is pass¹ in the denominator. That makes the cost curve far cheaper to resolve than the reliability contrast, which is exactly the right property when the budget is $200.

03

The sample

random, nested, unfiltered — and why that is the stronger choice

We draw a random sample of DeepSWE tasks and run every arm on all of them. No screening on difficulty, no screening on length, no screening on anything. The sample is a prefix of a larger sample, so more tasks can be added later and pooled cleanly.

Why not filter on baseline pass rate

The trap this avoids

The tempting move is to keep only tasks the model solves sometimes — pass rate in [0.25, 0.75] — because a strategy cannot lower a success rate that is already zero. It is a real efficiency gain and it is statistically wrong.

You would be selecting on the outcome, measured with the same noise as the outcome, using runs from the control arm. Tasks whose true rate is 0 or 1 but which got a lucky draw land in the band, then regress to the mean on fresh runs. The FULL arm therefore looks artificially inconsistent relative to treatment arms measured on clean runs — biasing the exact contrast H1 is about. Random sampling removes the problem entirely rather than mitigating it.

Two more reasons the unfiltered sample wins:

  • The estimand is the one you want. "Over DeepSWE tasks, tightening the budget costs X" is a population statement. Conditioning on mid-range difficulty gives a conditional quantity nobody asked about and everybody has to have explained to them.
  • Nothing to defend. A selection rule is the first thing a reviewer interrogates. "We drew a random sample" ends that conversation.

Why not filter on length either

Cost is roughly quadratic in run length, so short tasks are dramatically cheaper — but long runs are precisely where compaction matters. Selecting short tasks selects away from the phenomenon, which is a worse bias than the saving is worth. Because budgets are set as a fraction of each task's own peak (§06), the treatment is applied at equal intensity regardless of length anyway, so the only argument for short tasks was money.

Bound cost with a uniform cap, not a biased sample

Set a step limit from E1's observed FULL distribution — roughly 1.5 × p90(steps) — applied identically to every task and every arm, plus a dollar cost_limit set high enough that it is a runaway guard rather than a treatment. Runs that hit a cap are scored reward=0 and the truncation rate is reported per arm. That is a uniform, pre-declared policy: it costs a little power, it costs no validity, and if one arm truncates more often that is itself a finding.

Make the sample nested, so extending is free

Most samplers do not guarantee that an n=12 draw is a prefix of an n=24 draw. Do the ordering yourself once, and every future extension pools cleanly with what you already ran:

sample.py — deterministic, nested, reproducible
import hashlib

def study_order(task_ids, salt="gaia-2026-08"):
    """A fixed pseudo-random ordering of all 113 tasks."""
    return sorted(task_ids,
                  key=lambda t: hashlib.sha256((salt + t).encode()).hexdigest())

ORDER = study_order(all_113_task_ids)
STUDY = ORDER[:12]        # now
# later, with more budget:  ORDER[:24]  then  ORDER[:48]  — strict supersets.
# Seeds extend the same way: 0,1,2 now; 3,4 later; 5-9 after that.
  • Tasks and seeds are both extendable. Adding tasks widens the sample; adding seeds sharpens the reliability axis. Neither invalidates a single run you have already paid for.
  • Fix the salt and record it. It is part of the analysis plan.
  • You may not re-draw the sample because it looks expensive. If the draw happens to contain several very long tasks, reduce K — never re-roll. Re-rolling to avoid cost is length filtering through the back door.

Choosing n and K — after E1, not now

An unfiltered sample means cost per run is whatever the benchmark hands you, so the allocation is decided by measurement:

affordable_runs = grid_budget / mean_cost_per_run        # mean, not median — long tasks dominate
n * K           = affordable_runs / 5                    # FULL + SUMMARIZE x2 + RETRIEVE x2

Priority:  n >= 12  first, then spend the remainder on K, with K >= 3.

Why n before K. With a ~37% base rate, a small unfiltered sample can plausibly contain no solvable task at all — and then the success curve is flat zero and cost-of-pass is undefined. Task diversity is the insurance against that; seeds sharpen a signal that task diversity has to first make exist. Planning point: n = 12, K = 3. E1 confirms or adjusts it.

Get the filtering benefit back in the analysis, not the design

Report the full-sample estimate as primary. Then, as a clearly-labelled secondary, report the same contrasts restricted to tasks that any arm solved at least once — a criterion symmetric across arms, so it does not privilege the control the way a FULL-arm filter would. You get the sharper conditional picture and the unbiased population number, and you never selected on the outcome when deciding what to run.

06

The knob and the arms

one method override, four strategies, three budget levels

mini-swe-agent is deliberately linear: every step appends to self.messages, and that one list is both the trajectory record and the model input. DefaultAgent.query() is the only method we touch.

The rule that makes this clean

Never mutate self.messages. Build a derived view. Because the log and the prompt are the same list, mutating it destroys our ground truth. Instead query() computes a view, sends the view, and appends the response to the full log. Result: a complete uncompacted trajectory for every run in every arm — which is what makes offline replay, cost re-pricing and a future memory analysis free.

gaia/agent.py — the entire intervention
# AgentConfig ships with cost_limit = 3.0 USD. At a $200 total budget one runaway
# run is 1.5% of everything. Set it from E1 and hold it constant across arms.

class ContextManagedAgent(DefaultAgent):

    def build_view(self) -> list[dict]:
        msgs = self.messages
        if self.strategy == "FULL" or self.token_budget is None:
            return msgs
        if exact_tokens(msgs, self.model) <= self.token_budget:
            return msgs                          # under budget: nothing to do

        head, body = msgs[:2], msgs[2:]           # system + instruction, ALWAYS kept
        room = self.token_budget - exact_tokens(head, self.model)

        if self.strategy == "PRUNE":
            return head + keep_last_that_fit(body, room)

        if self.strategy == "RETRIEVE":
            q = subgoal_query(msgs)               # CURRENT subgoal, not the static task
            return head + hybrid_topk(body, query=q, budget=room,
                                      pin=writes_and_last(body))

        if self.strategy in ("SUMMARIZE", "SUMMARIZE_T0"):
            recent = keep_last_n(body, self.keep_recent)
            older  = body[:len(body) - len(recent)]
            t = 0.0 if self.strategy == "SUMMARIZE_T0" else self.summ_temperature
            self.note, c = self.summarizer(
                SLOT_PROMPT + serialize(older, prior=self.note), temperature=t)
            self.summarizer_cost += c             # model.cost does NOT see this
            self.compactions += 1
            view = head + [{"role":"user",
                            "content": f"[COMPACTED MEMORY]\n{self.note}"}] + recent
            if exact_tokens(view, self.model) > self.token_budget:
                # recent turns alone can exceed a tight budget — shrink, then record it
                view, dropped = shrink_recent(view, self.token_budget, self.model)
                self.log_event("recent_overflow", dropped=dropped)
            return view

    def query(self) -> dict:
        view = self.build_view()
        self.log_view(view)
        response = self.model.query(view)                        # model sees the VIEW…
        self.add_messages({"role":"assistant", **response})     # …log keeps EVERYTHING
        self.log_usage(response)                                 # incl. cached tokens
        return response

Three details in that code that matter

  • exact_tokens, not an estimate. The budget is the study's independent variable; measurement error in the treatment itself is the one place a heuristic is unaffordable.
  • The recent-turns overflow guard. head + note + recent can exceed the budget when the last bash observations are large — exactly the tight-budget regime we care about.
  • Summarizer cost tracked separately. model.cost only sees the agent's own calls. If summarizer tokens are invisible, cost_limit lets the summarize arm run longer for the same nominal budget — a confound that flatters our own suspect.

Budgets: absolute token values (decision 2026-08-28)

Absolute, like production — a dated design change 
budget(level) = one token value for EVERY task   (set by E2 from E1's measured peaks)

   TIGHT: >=1 compaction on >=75% of tasks, >=3 on >=50%     LOOSE: treats 30-50%

The earlier draft set budgets per task as a fraction of its own peak — cleaner dose control, but a task-level oracle: no engineer can set "20% of this task's eventual peak." The production knob is absolute, so the study's axis is absolute. The cost, accepted knowingly: at any absolute budget the short tasks never compact — the arms are identical there — so H1's effective sample shrinks to the treated tasks (treated share reported per level; the power simulation models the dilution). That mixture is not a bias: it is exactly what deploying that budget does to a real workload, and treatment status is determined by task length, a pre-treatment covariate, so restricting the H1 contrast to treated tasks is legitimate and pre-declared.

Acceptance test: at LOOSE, ≥30% of the sample compacts at least once. At TIGHT, ≥80% compacts ≥3×, the median view still carries ≥1.5× the head in real history, and the overflow guard trips on <10% of steps. If no value pair satisfies the targets, adjust the values — never the sample.

Use ctrf_pass_fraction. ctrf.json reports per-assertion results, so even a failing run yields a graded score. At a ~37% pass rate most runs fail, and a binary outcome throws away nearly everything in them. On an unfiltered sample that matters even more: tasks the model never solves still carry graded information about whether a tighter budget made it get less far. This may be the difference between a visible curve and noise. Keep reward as the primary so the headline stays leaderboard-comparable.

The cost model

p = input price/token · 0.1p = cached price · L_t = context at step t

cost(call t) = 0.1p·L_(t-1) + p·d_t + p_out·out_t
               ^^ cached prefix   ^^ new suffix

FULL over n steps:  input ≈ p·L·(1 + 0.05n)
                    # each token paid once at full price, then 10% forever

A compaction voids the cache -> the next call pays FULL price on the new view V:
    penalty = p·V                     saving = 0.1p·(L−V) per later call
    break-even  m* = 10V / (L − V)

    V=32K, L=120K -> m* ≈ 3.6 calls      V=64K, L=120K -> m* ≈ 11.4
    V=32K, L=200K -> m* ≈ 1.9 calls
What the arithmetic predicts

Compactions are tens of calls apart and m* is single-digit at a tight budget, so compaction does reduce raw dollars, monotonically. Raw cost is the boring quantity. Cost-of-pass is the interesting one — cost falls, accuracy falls, and the ratio has a minimum. That is H2.

A useful budget consequence: your treatment runs are cheaper than your control runs. PRUNE is cheapest of all — no summarizer, no embeddings — which is why it earns a place as the cost floor.

09

Analysis, and the one plot

what to compute and how to report it honestly at 12 tasks, K = 3

The figure everything is for

One plot. X-axis: budget fraction, 20% → 100%. Three normalised curves: success, consistency (all@3), and cost-of-pass, inverted. Shade the band where cost-of-pass sits within its bootstrap CI of the minimum. That shaded band is the recommended operating range — the thing an engineer pins on the wall. Every experiment in §07 exists to draw it.

Standing rules

  • Everything paired. At 12 tasks a between-task comparison is a shrug with error bars. Same task, same seed, SUMMARIZE vs RETRIEVE at the same budget fraction. Bootstrap resamples tasks — 10,000 draws.
  • Report H1 as an estimate, not a test. Give the Δ contrast with its CI and say plainly that 12 tasks at K=3 cannot settle it. A pilot that labels itself correctly is credible; one that oversells is not.
  • Exclusions. error excluded, rate reported. step_limit / cost_limit / timeout scored reward=0 and reported as per-arm rates — if summarize truncates more often, that is a result.
  • No mixed model. At 12 tasks it will not converge meaningfully. Paired bootstrap only, and say so.
  • Report the full sample as primary, the conditional view as secondary. Give every contrast over all 12 tasks first. Then repeat it restricted to tasks any arm solved at least once — a criterion symmetric across arms, so it does not privilege the control the way a FULL-arm filter would. Label it exploratory. That recovers the sharpness a filtered design would have had, without ever selecting on the outcome.
  • Publish the power calculation that the pilot's effect sizes imply. It is the bridge to the funded study, and reviewers read it as competence.

When a gate fails

decided now, so it is not decided under pressure with $30 left

FailureDo this
E00 no cached tokens through the proxy worst caseTry Gemini directly if you have a native key. If not: re-forecast at ~5× cost, which means drop to K=2 and one treatment budget — keep all 12 tasks. The cost axis becomes modelled via §08's arithmetic rather than measured. Say so explicitly.
E00 thinking tokens dominateFix a low reasoning effort, hold it constant everywhere, record it as a study parameter and a limitation.
E0 neither integration path worksRun mini-swe-agent directly against the Harbor containers and invoke the verifier yourself. Slower, no orchestration — the study survives.
E1 the sample is more expensive than plannedReduce K, never the sample. Re-drawing to avoid expensive tasks is length filtering through the back door, and it reintroduces exactly the bias §03 exists to avoid. K=2 still gives all@2, which is a weak but honest consistency measure.
E1 the draw contains no solvable task the unfiltered-sample riskThis is the real cost of not filtering, and the guard against it is n before K. If seed-0 FULL solves nothing across 12 tasks, extend to ORDER[:20] at K=1 (+$10) before spending on the grid — widening the sample is legitimate, screening within it is not.
E2 no fraction pair passes the acceptance testAdjust the fractions, not the sample. If even 10% of peak fails to force compaction, the head floor is dominating and the study needs longer tasks — which the next sample extension will supply.
E5 spend exceeds E2's prediction by >25%Stop the block and diagnose. This is exactly what the prediction exists for.
E5 most tasks fail in every armExpected on an unfiltered sample at a 37% base rate. The aggregate pass rate is still the population estimate, cost-of-pass is still defined as long as it is above zero, and the secondary conditional analysis (§09) recovers the sharper view.
E5 no reliability signalExpected at this N. Check the cost axis — H2 is independent of H1, and the operating point is the result engineers will actually use.
E5 summarize beats retrieveReport it, then check cost-of-pass. Three axes means any direction is a result.

Four of the eight experiments cost nothing — the pre-flight, the replay calibration, the power simulation, and the re-pricing.
